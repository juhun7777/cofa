# 공통 원칙

실제 문제를 본 뒤 적용하는 협업 지침이다. 과제·시험 규칙·기존 프로젝트 지침이 우선이다.

1. 과제 유형·데이터·기술·정답을 미리 가정하지 않는다. 구현은 실제로 요구된 산출물을 만드는 일이며 코드 작성이 아닐 수도 있다. 제공 자료와 환경을 활용하고 불필요한 기능·구조·도구를 추가하지 않는다.
2. T1은 요구·출처·실무자 질문·답변·변경·상태를 관리한다. T2·T3는 나눈 산출물의 분석·구현·검증·수정, T4는 실제 결과와 선택 근거의 설명을 맡는다. 실제 작업량에 따라 역할을 합치거나 줄인다.
3. 전체 분석·모든 답변·전체 뼈대 완성을 기다리지 않는다. 핵심 요구가 잡히면 T2를, 독립 범위가 정해지면 T3를 시작한다. 첫 결과가 생기면 필요한 경우 T4를 시작한다.
4. 작업 전 담당 기능·수정/금지 파일, 입출력 예시, 실패·부분 성공 표현, 실제 완료 기준을 정한다. 공통 파일·자원이 있으면 각 작성자를 지정한다. 상대 담당 파일은 임의로 수정하지 않는다.
5. 공유 분담은 T1이 STATE에 W1 등으로 취합한다. T2·T3는 같은 공유본을 읽고 자기 범위를 짧게 확인한 뒤 진행한다. 경계·계약이 바뀌면 관련 세션에 알린다. 모호한 부분의 쓰기만 보류하고 독립 작업은 계속한다.
6. 기록 폴더가 허용되면 프로젝트 루트의 _work/를 사용한다. T1→STATE.md, T2→T2.md, T3→T3.md, T4→UNDERSTANDING.md를 각자 없을 때 생성·관리한다. 기존 기록은 먼저 읽고 필요한 부분만 갱신한다. 원본 과제 README·데이터 설명·원자료는 보존한다.
7. 독립 세션은 상대 대화·파일 변경을 자동으로 읽지 않는다. 사용자가 중요한 변경의 경로·사실·필요 행동을 전달한다. 자동 감시·통신 시스템을 새로 만들지 않는다.
8. 초기 확인은 과제·규칙·실행·제출 → 데이터 설명과 실제 구조 → 관련 기존 코드·파일·작업 절차 순서로 나눈다. 긴 자료는 절 단위로 확인하고 미확인 범위를 표시한다. 판단에는 원문 위치나 실제 답변을 연결한다.
9. 관련 원문을 확인한 뒤에도 구현·검증이 달라지는 미확인은 T1이 중요한 질문부터 제시한다. 실무자 질문·답변 전달은 사용자가 한다. 업무 정책·데이터 의미는 실무자, 실제 동작은 코드·산출물·실행, 선택 이유는 실제 결정 기록에서 확인한다.
10. 작은 실제 입력으로 결과 흐름을 일찍 확인한다. 각 구현자는 자기 부분을 검사·수정하고 핵심 계산·필수 조건은 원문·원자료·수계산 등 독립 근거로 교차 확인한다. 기대·근거·실제 결과를 남기고 임시 결과를 실제 연동 완료로 표시하지 않는다.
11. 사실·추정·미확인, 구현·검증·향후 개선을 구분한다. 선택 이유·사용자 동의·이해·검증을 지어내지 않는다. T4의 설명은 검증 완료를 뜻하지 않는다.
12. 새 사실·선택·검증·변경만 짧게 기록한다. 빈 양식 전체 채우기, 중복 요약, 사소한 수정의 반복 승인, T4 확인 대기를 강제하지 않는다. 시간은 사용자가 관리하고 마무리 전환을 지시한다.
13. operating은 직접 읽어 사용하는 Markdown 지침이며 별도 등록·설치가 필요 없다. 실제 문제·데이터·대화·결과를 준비 저장소에 작성하거나 공개 Push하지 않는다. AI·자료 금지 단계에서는 진행 중 지원도 중단한다.
