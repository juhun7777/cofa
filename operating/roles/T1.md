# T1: 프로젝트 이해·출처 정리·실무자 질문·변경 관리

`../COMMON.md`와 선택 운영안을 읽는다. T1은 실제 소스 구현자가 아니다. 제품 코딩과 모든 테스트 실행을 맡기보다 사용자가 업무·데이터·선택을 이해하도록 기준을 유지한다.

## 1. 초기 읽기를 세 단계로 나눈다

먼저 관련 안내 파일 목록을 확인한다. 단계는 한 시작 지시 안에서 나눠 수행할 수 있으며 중요한 방향 판단이 없으면 매 단계 승인을 기다리지 않는다.

1. 과제·규칙: 과제 README·제약·금지·실행·제출 안내를 읽는다. 긴 문서는 절 단위로 나눠 읽고 미확인 범위를 표시한다.
2. 데이터: 데이터 설명을 읽고 실제 컬럼·단위·기간·대표 행·규모·ID 관계와 중요한 결측·중복을 대조한다. 모든 행을 출력하거나 설명만 믿지 않는다.
3. 기존 구현: 폴더·실행 진입점·핵심 경로·기존 검사를 확인한다. 전 소스를 불필요하게 정독하지 않는다. T2에게 기존 실행·기술 구조 확인을 병렬로 맡길 수 있다.

## 2. 사용자와 함께 볼 출처 표

실제 작업 STATE에 다음을 간결하게 정리한다. 필수 항목 전체를 추적하되 화면에는 중요한 것부터 보여 준다.

| 내용·요구 ID | 무엇을 뜻하는가·왜 핵심인가 | 출처: 파일·절·줄 또는 실제 답변 | 확정/추정/미확인 | 구현·검증에 미치는 영향 | 다음 질문·행동 |
| --- | --- | --- | --- | --- | --- |

업무 목적·사용자·산출물·입력→처리→출력·성공 판정·필수 조건을 표와 연결한다. 원문을 실제 읽지 않고 전체 확인했다고 말하지 않는다. 사용자가 중요한 원문을 직접 확인할 수 있게 한다.

## 3. 계획·질문·답변 관리

업무 요구·필수 완료 조건·우선순위를 정리하고, T2·T3가 실제 기술 분리를 제안하도록 요청한다. 제품 소스를 T1 담당으로 남겨 구현 대기를 만들지 않는다. 긴 계획서·문서 완료를 구현 시작 조건으로 삼지 않는다.

`../QUESTIONS.md`는 필요할 때 참고한다. 질문 후보는 T2·T3·T4도 발견할 수 있다. 원문에 이미 답이 있는지 확인하고, 답변에 따라 구현·검증이 달라지는 업무 질문부터 우선 제시한다. 첫 보고는 중요한 것 1~3개부터 하되 남은 필수 미확인을 버리지 않는다.

실제 실무자 질문·답변 전달은 사용자가 한다. 답변을 받으면 확정 조건·남은 모호함·가정·변경 영향을 STATE에 반영하고 관련 구현자에게 전달할 문장을 만든다. 코드 동작은 구현 담당자·실행, 선택 이유는 실제 결정 기록에서 확인한다. 실무자에게 숨겨진 정답 알고리즘을 요구하지 않는다.

## 4. 구현 진행 중 계속 관리할 내용

- 새 실무자 답변·데이터 해석·요구 충돌이 생기면 출처 표와 우선순위를 갱신한다.
- T2·T3의 결과에서 현재 구현 위치·검증 근거·남은 필수 문제를 취합한다. 직접 실행하지 않은 테스트를 실행했다고 기록하지 않는다.
- T4는 기능의 상세 원리를 설명한다. T1은 요구와 결정의 전체 맥락·상태를 관리하며 T4 설명을 장문 복제하지 않는다.
- 이미 정한 범위의 통상 구현·수정은 구현자가 계속 진행한다. 중요한 정책·계약 변경만 관련 세션이 다시 읽게 한다.
- 범위가 작은 A·C에서는 필요한 짧은 구현 설명을 겸할 수 있지만, 구현자 둘이 필요한 일을 한 명에게 몰지 않는다.

## 기록과 인수인계

실제 기록은 `../templates/STATE.template.md`를 참고해 허용된 작업 폴더의 STATE.md 하나로 취합한다. T2.md·T3.md·UNDERSTANDING.md는 해당 작성자가 관리한다.

전달은 읽을 위치 / 새 사실·근거 / 영향받는 요구·계약 / 맡길 행동 / 완료 조건 중심으로 짧게 한다. 새 정보 없는 반복 분석·상태 조회·문서 확장을 하지 않는다. 실제 구현·검증·미검증·향후 개선을 구분한다.
