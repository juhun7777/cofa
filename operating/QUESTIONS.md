# 실무자 질문·코드 확인·본인 이해

일반 준비용 질문 틀이다. 실제 기출·시험 원문·특정 출제 방식이나 채점 기준이 아니다. 모든 질문을 한꺼번에 사용하지 않는다.

## 어디에 물을 것인가

| 모르는 내용 | 확인할 곳 | 예시 |
| --- | --- | --- |
| 업무의 목적·우선순위·허용 행동 | 원문에 없으면 실무자 | 비용 절감과 처리 지연이 충돌하면 어떤 기준을 우선하는가? |
| 컬럼 의미·업무상 결측·집계 기준 | 데이터 README·원자료, 여전히 모호하면 실무자 | 이 수량은 등록 건수인가, 해당 기간의 실제 발생 건수인가? |
| 현재 구현의 동작·저장·실패 | 실제 코드와 실행, 구현 담당자 | 중복 요청 시 현재 함수는 새 결과를 만드는가? |
| 대안 알고리즘과 절충점 | AI와 분석하되 사용자 판단, 실제 비교 | 이 데이터·시간·제약에서 어느 대안이 유리하며 무엇을 포기하는가? |
| 자신이 설명할 수 있는지 | 본인이 먼저 답하고 코드 근거로 점검 | 입력 한 건이 어떤 함수와 저장소를 거쳐 결과가 되는가? |

실무자에게 AI 코드의 원리나 숨겨진 정답 알고리즘을 대신 설명해 달라고 요구하지 않는다. 업무 정책은 확인하고 기술 선택은 데이터·조건·비교 근거를 갖고 판단한다.

## 언제 질문을 제안할 것인가

모든 README와 데이터 확인이 끝날 때까지 질문을 미루지 않는다. 관련 원문에서 답을 먼저 찾되, 구현 방향·필수 조건·성공 기준에 영향을 주는 미확인이 나오면 해당 시점에 중요한 질문 1~3개부터 사용자에게 제시한다. 아래 시점은 질문을 세 번만 하라는 뜻이 아니며 실제 정보가 생길 때 적용한다.

| 시점 | 확인하고 질문할 내용 |
| --- | --- |
| 초기 요구사항 파악 중 | 업무 목적, 필수 기능, 성공 기준, 구현 방향을 바꾸는 우선순위 |
| 데이터 확인 중 | 컬럼·단위·ID의 의미, 누락·중복 처리, README와 실제 데이터의 불일치 |
| 구현·검증 중 | 실패·부분 성공 정책, 예외 상황, 결과를 실제 업무에 적용할 기준 |

질문마다 관련 원문·데이터에서 확인한 사실, 아직 모르는 부분, 답에 따라 달라질 구현·검증을 짧게 붙인다. 답을 기다리는 동안 영향받지 않는 분석·구현·검증 준비는 계속한다. 답이 필요한 부분은 미확인 상태를 표시하고 업무 정책을 임의로 확정하지 않는다. 질문 내용이 기술 선택·코드 동작이면 실무자 대신 관련 구현자와 코드·실행에서 확인한다.

## 질문 생성·답변 반영 절차

T2·T3가 담당 분석·구현·검증 중 의문 발견, 또는 T4가 선택 이유 누락·코드 모순 발견 → 자기 기록에 근거·영향 작성 → T1이 원문·중복 확인 → 사용자가 실무자에게 업무 질문 → 답변을 T1에 전달 → STATE의 요구·결정·변경 영향 갱신 → 구현자와 설명 담당이 해당 부분을 다시 읽고 반영.

독립 터미널 간 단계는 사용자의 짧은 인수인계를 기본으로 한다. 자동 감시·API·파일 통신 프로그램을 새로 만들지 않는다.

## 질문 한 개의 형식

```text
[미확인 조건] 무엇을 모르는가?
[근거] 어떤 원문·데이터·현재 구현을 확인했는가?
[영향] 답에 따라 어떤 구현·검증·성공 판정이 바뀌는가?
[실무자에게 보낼 질문] 구체 사례로 묻는 짧은 문장
[모호할 때 후속 질문] 우선순위·허용 범위·예외 중 무엇을 더 확인할까?
[상태] 미질문 / 일부 답변 / 확인 / 미해결 가정
```

답에 따라 할 일이 바뀌지 않는 질문은 우선순위를 낮춘다. 원문에 답이 있는 질문은 다시 묻지 않는다. 첫 보고는 중요 질문 1~3개부터 하되 남은 중요한 불확실성을 없던 것으로 하지 않는다.

## 일반 예시

| 넓은 질문 | 구체적인 후속 질문 |
| --- | --- |
| 효율이 중요하다는 답변 | 총비용은 감소하지만 최대 처리 시간이 증가할 때, 넘으면 안 되는 시간과 우선순위는 무엇인가? |
| 데이터가 일부 누락될 수 있다는 답변 | 누락 항목을 제외한 결과를 제공해도 되는가, 전체 처리를 중단해야 하는가, 별도 정책이 있는가? |
| 여러 사람이 쓴다는 답변 | 같은 초안을 두 사람이 수정한 뒤 순서대로 적용하면, 나중 수정으로 덮어써도 되는가, 충돌 확인이 필요한가? |
| 최신 결과를 보여 달라는 답변 | 생성 시점과 승인·적용 시점 중 어느 때부터 최신 결과로 간주하는가? |
| 재실행 가능해야 한다는 답변 | 같은 입력을 다시 실행하면 새 결과가 필요한가, 기존 결과를 반환해야 하는가? |

선택지 밖의 정책도 허용해 잘못된 양자택일로 답을 유도하지 않는다. 운영상 예외를 제시받았다고 필수 제약을 임의 완화하지 않는다. 답이 모호하면 아직 미해결로 표시하고 가정·영향·변경 위치를 남긴다.

## 현재 구현을 검토한 뒤 질문 갱신

T1에게 다음처럼 요청한다.

```text
STATE, T2·T3의 구현·검증 기록, T4의 UNDERSTANDING과 실제 코드를 대조해 지금 부족한 정보만 찾아 줘.
실무자에게 확인할 업무 규칙 / 코드로 확인할 동작 / 내가 이해해야 할 선택을 구분해 줘.
실무자 질문은 이미 확인한 근거와 답에 따라 바뀌는 부분을 붙여 중요한 것부터 제안해 줘.
새로운 실제 정보가 없으면 같은 질문 목록이나 설명 문서를 반복 생성하지 마.
```

## 구현 이해 점검 — AI 사용이 허용된 과제 단계에서만

아래는 일반적인 기술 설명 점검 주제다. 실제로 만들어진 내용에서 필요한 것만 고른다.

- 선택과 절충: 문제 정의·목적·필수 제약·알고리즘·대안·선택 이유·실패 조건.
- 실행 흐름: 입력→검증→핵심 처리→저장→결과 제공과 실제 함수·파일 위치.
- 변경과 실패: 중복·동시 수정·오래된 입력·부분 실패·재실행에서 실제 동작과 미구현 보호 장치.
- 요구 준수: 원문 요구와 구현·검증 연결, 정상·경계·실패 사례, 미검증 사항.
- 추가 실험: 검증할 가설, 필요한 데이터, 비교 조건, 지표, 결과에 따라 판단을 바꿀 기준.
- 과제에 관련될 때만: 데이터 누수·분모·편향, 권한·노출, 계산 비용·규모 증가, 재현성·운영 관측.

```text
현재 구현한 핵심 부분 하나를 실제 입력 예시로 짧게 설명해 줘.
구현·검증한 것과 추후 개선을 구분하고 관련 함수·저장 위치를 짚어 줘.
내가 이해했는지 확인할 사례 질문 한 개를 내되 정답은 먼저 공개하지 마.
내 답변 후 실제 코드와 결과에 근거해 맞는 부분과 잘못된 부분을 교정해 줘.
```

말로 그럴듯하게 답한 것을 검증 완료로 기록하지 않는다. 사용자의 의도·선택·이해를 지어내지 않는다. AI·자료 열람이 금지된 단계에서는 이 자료를 통한 지원도 하지 않는다.
