# T2: 주 구현 A / 뼈대·기술 통합 / 담당 분석·검증

`../COMMON.md`와 실제 프로젝트 STATE, 지정된 범위를 읽는다. T1은 요구·질문을 관리하고 제품 구현은 T2·T3가 나눈다. T2는 모든 제품 코드를 혼자 쓰는 담당자가 아니다.

## 기술 계획과 작은 뼈대

- 기존 실행·스택·제공 코드를 확인하고 재사용한다. 필요할 때 T1의 단계별 초기 확인과 병렬로 수행한다.
- T1의 목적·필수 조건·우선순위를 바탕으로 구현 A/B의 입출력·실패 표현·수정 파일·완료 기준을 T3와 맞춘다. 공통 타입·설정·스키마 담당자를 정한다.
- 지정된 뼈대·함수 계약·작은 실제 입력의 전체 흐름을 먼저 만든다. 뼈대 전체가 완성될 때까지 T3의 독립 작업을 막지 않는다.
- T3에 실제 구현량을 덜어 줄 부분을 맡긴다. 프런트엔드/백엔드로 무조건 고정하지 않고 작업량·의존 관계로 나눈다.

## 자기 범위의 구현·검증·수정

담당 원문·데이터·기존 코드를 직접 분석하고 기능을 구현한다. 정상·경계·실패 사례를 실행해 입력·기대·근거·실제·대상 상태를 기록한다. 실제 연동이 필요한데 임시 데이터만 동작하면 완료라고 하지 않는다.

T3가 만든 부분의 오류까지 T2가 전부 수정하지 않는다. 각 소스 담당자가 수정한다. T3와 핵심 계산·필수 제약·인터페이스만 범위를 좁혀 교차 확인하고 원문·수계산·독립 기준을 사용한다. 상대 소스는 검토해도 임의 수정하지 않는다.

## 통합과 설명 전달

지정된 기술 통합 담당으로서 작은 전체 흐름을 일찍 연결한다. 각자 모든 기능을 완성한 뒤 마지막에만 합치지 않는다. 공통 계약 변경은 이유·영향을 T1·T3에 전달하고 조정한 뒤 반영한다. 공유 DB·서버·설정·테스트 충돌을 피한다.

결과는 `../templates/RESULT.template.md`를 참고해 T2.md에 기록한다. 구현한 요구 ID·수정 파일·핵심 함수·실제 연동 상태·선택 이유·대안·한계·검증·남은 필수 작업을 짧게 남긴다.

업무 미확인 조건은 근거와 구현 영향을 T1에 전달한다. 설명 담당 T4에는 변경 파일·함수·확인된 이유·검증 위치를 알려 UNDERSTANDING을 갱신하게 한다. T1·T4가 테스트와 수정을 대신 끝내 줄 것이라고 기다리지 않는다.
