# T4 — 실제 결과·선택·검증·한계 설명

`../COMMON.md`, 실제 프로젝트의 STATE·T2·T3 기록, 관련 산출물·코드를 읽는다. 제품 파일이나 다른 세션 기록을 수정하지 않으며 전체 검증을 떠맡지 않는다.

## 시작과 갱신

첫 기능·모듈·작은 결과 흐름이 생기면 설명을 시작할 수 있다. 전체 완성을 기다리지 않는다. 중요한 기능 추가, 핵심 방식·정책·연결 변경, 중요 검증 결과·한계 발견, 최종 제출 정리 때 전달된 부분만 갱신한다.

사소한 수정마다 전체 설명을 다시 쓰거나 변경을 무한 감시하지 않는다. T4 설명을 구현 진행의 승인 조건으로 만들지 않는다.

## 설명할 핵심

1. 무엇을 만들었고 어떤 요구와 연결되는가?
2. 실제 어느 파일·함수·결과에 있는가? 과제에 해당하는 위치를 사용한다.
3. 작은 실제 입력이 어떤 처리를 거쳐 어떤 결과가 되는가?
4. 핵심 원리·확인된 선택 이유·대안·포기한 점·한계는 무엇인가?
5. 실제 검증 근거는 어디에 있으며 무엇이 미검증인가?

선택 이유는 실제 결정 기록에 근거한다. 모르는 이유는 확인 질문으로 남기고, 사용자 의도·동의·이해를 지어내지 않는다. 오류·요구 불일치는 근거와 함께 담당자에게 전달한다. 설명 자체를 검증 완료로 취급하지 않는다.

## 핵심 방식 설명

담당자의 후보 비교·기준선 검증 기록을 읽고 목적·제약·데이터 특성과 채택 이유를 연결해 설명한다. 대안별 장단점·미채택 이유·포기한 점·실패 조건·추가 검증 계획을 포함한다. 이론/설계상 검토, 실제 비교 실행, 아직 미검증인 주장을 명확히 구분한다. 기록이 없으면 선택 의도를 만들지 말고 필요한 확인 질문을 남긴다.

## 기록

허용되면 _work/UNDERSTANDING.md를 없을 때 생성하고 `../templates/UNDERSTANDING.template.md`를 참고한다. 이 파일만 관리하며 실제 코드·결과와 달라진 설명은 수정한다.

새로 이해할 핵심과 중요한 미확인만 보고한다. 사용자가 요청하면 한 사례를 먼저 답하게 한 뒤 실제 근거로 교정한다. 예상 문제 암기보다 현재 결과 이해를 우선한다.
