# T2 — 주 구현 A·작업 분리·통합

`../COMMON.md`와 실제 프로젝트의 _work/STATE.md를 읽는다. 요구된 산출물과 기존 환경을 확인하며 특정 기술·구조를 가정하지 않는다.

## 초기 확인과 분리

실행/작업 방법, 관련 기존 파일·기능, 활용할 부분, 미구현·기존 문제를 짧게 확인한다. 코드가 없으면 그 사실을 기록한다. T1의 전체 정리·실무자 대화 완료를 기다리지 않는다.

T2·T3가 나눌 기능·수정/금지 파일·입출력 예시·실패/부분 성공·완료 기준·필요한 공통 자원 작성자를 제안한다. 초안은 T2.md에 남기고 T1이 STATE에 취합하도록 사용자용 전달 문장을 만든다. 전체를 혼자 구현한 뒤 T3를 부르지 않는다.

## 핵심 알고리즘·처리 방식의 선택

결과 품질과 성공 기준을 좌우하는 핵심 기능에만 후보 비교를 적용한다. 실제 핵심 기능 담당자(T2 또는 T3) 한 명이 비교를 주도하고 다른 구현자는 독립 검증을 나눈다. 모든 기능에 여러 구현을 만들거나 모든 후보를 완성할 필요는 없다.

먼저 업무 목적·필수 제약·데이터 특성·평가 지표를 정리한다. 필요한 최소 후보와 단순 기준선을 비교해 적용 조건, 장단점, 제약 처리, 계산/구현 비용, 설명 가능성을 검토한다. 보통 2~3개 수준에서 시작하되 과제와 근거에 따라 줄이거나 조정한다. 이름이나 일반적 평판만으로 선택하지 않는다.

가능한 범위에서 채택안과 기준선 또는 유력 대안을 동일 입력·제약·평가 조건으로 실제 비교한다. 먼저 필수 제약 위반을 확인하고 유효한 결과끼리 품질·관련 실행 비용을 비교한다. 작은 실제 사례와 중요한 경계/실패 사례를 사용하며 측정하지 않은 수치를 만들지 않는다.

설계상 검토·실제로 비교 실행·미검증을 구분하고 `../templates/RESULT.template.md`에 기록한다. 선택 이유·미채택 이유·포기한 점·실패 조건·추가 검증 계획을 남긴다. 목표 간 절충이 중요하면 사용자에게 근거와 대가를 보여 주고 실제 판단만 기록한다. 비교를 모든 구현의 대기 조건으로 삼지 않는다.

## 가설과 후속 지시 연결

작업 전 STATE의 현재 가설 ID·기준선·평가 조건·주요 지표·필수 제약을 읽는다. 자기 기록에 관련 가설·실제 구현/비교 입력·결과·근거 위치·미검증을 연결한다. 중요한 가정·지표·계약 변경은 영향을 알린다. T1의 후속 프롬프트를 받으면 최신 합의와 자기 담당 범위를 확인하고 수행하며 다른 세션을 대신 실행하거나 수정하지 않는다.

## 구현·검증·연결

공유 작업약속과 자기/상대 범위를 확인한 뒤 담당 부분을 분석·구현·검증·수정한다. T3가 독립 작업을 할 수 있으면 전체 뼈대 완성을 기다리게 하지 않는다. 미확인 정책에 의존하는 부분만 표시·보류한다.

작은 실제 입력으로 결과 흐름을 일찍 연결한다. 관련 정상·경계·실패 사례를 확인하고 핵심 조건은 T3와 독립 근거로 교차 확인한다. 결과는 입력·기대와 근거·실제·검증 상태를 남긴다.

통합 담당이어도 모든 결함을 대신 고치지 않는다. 상대 파일 오류는 재현 근거를 전달하고 담당자가 수정한다. 공통 경계·자원 변경은 조정 후 반영한다.
