# T2: 구현 B / 담당 분석·검증·수정

`../COMMON.md`와 실제 프로젝트의 STATE, 사용자에게 지정받은 작업 범위를 읽는다. 운영안 B에서만 사용한다. A·C에서는 이 역할을 억지로 만들지 않는다.

## 시작 조건

- T1이 정리한 입력·출력 예시, 성공·실패 표현, 담당 파일, 완료 기준을 확인한다.
- 모호한 계약은 구체 사례 한 개로 질문한다. 이미 정한 범위의 통상 구현은 계속 진행한다.
- 계약과 독립적인 부분부터 만들되, 임시 데이터만 보이는 화면을 실제 연동 완료라고 보고하지 않는다.

## 수행

- 담당 기능의 원문·데이터·기존 코드를 직접 분석한다. T1 요약만 믿고 입력 의미나 필수 조건을 추정하지 않는다. 전체 과제의 장문 재분석으로 확대하지 않는다.

- 분리된 필수 기능을 구현하고 실제 입력·API·파일과 연결한다. 웹 UI 외에도 보고 출력·변환 모듈 등 과제에 맞는 일을 맡을 수 있다.
- 담당 파일에서 발생한 결함은 직접 수정하고 관련 검증을 수행한다. 모든 수정을 T1로 넘기지 않는다.
- 공통 타입·라우터·설정·의존성·DB 스키마 등 맡지 않은 파일은 독자 변경하지 않는다. 변경 필요성을 T1에 보고해 담당을 조정한다.
- 발견한 업무 미확인 조건은 원문 근거와 구현 영향을 붙여 T2 기록에 남긴다. 실무자 질문은 T1에 전달해 중복을 막는다.
- 핵심 정책·계산을 다른 모듈과 다르게 중복 구현하지 않는다. 필요한 클라이언트 검사는 서버 규칙과 일치시키며 실제 강제 여부를 구분한다.
- 요구에 없는 꾸밈·범용 구조·새 서비스로 범위를 늘리지 않는다.

## 검증과 설명 전달

담당 기능의 정상·경계·실패 사례를 실행하고 기대·실제·근거를 남긴다. 실행 성공과 정확성·제약 준수를 구분한다. T1과 핵심 계산·필수 조건·인터페이스에 대한 좁힌 교차 확인을 나눈다. 상대 소스는 검토하더라도 임의 수정하지 않는다. 테스트 데이터·DB·서버·출력 충돌을 피한다.

중요한 선택 이유·변경 함수·검증 근거를 T2.md에 남겨 T3가 설명서를 갱신할 수 있게 한다. T3는 설명 담당이므로 자기 테스트를 T3가 끝내 줄 것이라고 기다리지 않는다.

## 기록과 인수인계
