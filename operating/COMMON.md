# 모든 세션의 공통 원칙

일반 Markdown 지침이며 자동 실행 프로그램이 아니다. 실제 과제·플랫폼 규칙과 기존 프로젝트 지침을 먼저 따른다.

1. 사용자가 알려준 프로젝트 루트·남은 시간·허용 도구·선택 운영안을 확인한다. 경로와 시간은 모르면 추정임을 표시한다. 지침 저장소의 폴더와 실제 프로젝트를 혼동하지 않는다.
2. T1은 요구·업무 질문·핵심 결정의 창구이자 주 구현자다. 중요한 선택의 추천안·이유·대가를 제시하고 사용자가 판단하게 돕는다. 이미 결정한 범위의 통상 구현·허용 검증은 반복 승인 없이 진행한다.
3. 처음에는 과제·데이터·실행·제출 안내를 실제로 읽는다. 요구사항의 출처를 남기며 사실·미확인·제안을 구분한다. 필수 항목 전체를 점검하되 화면 보고는 중요한 내용부터 짧게 한다.
4. 독립 터미널은 다른 터미널 대화를 자동으로 알거나 지휘하지 못한다고 가정한다. 인수인계 때 읽을 기록 파일과 변경 내용을 명시한다. 파일을 바꿨다고 상대 세션의 맥락이 자동 갱신되지 않는다.
5. 실제 작업 메모는 허용된 프로젝트 안의 전용 작업 폴더에 둔다. 기본 예시는 `_work/`이며 기존 폴더와 충돌하면 T1이 다른 경로를 정한다. 내려받은 준비 저장소에는 실제 문제·데이터·기록을 쓰지 않는다.
6. T1만 `STATE.md`, T2만 `T2.md`, T3만 `T3.md`를 갱신한다. 제품 소스·공유 타입·설정·테스트 파일의 수정 범위는 STATE의 담당표로 정한다. 맡지 않은 파일을 수정해야 하면 변경 이유를 보고하고 범위를 먼저 조정한다.
7. 원본 README·데이터를 덮어쓰지 않는다. 기존 스택·실행 방식을 우선하고 요구되지 않은 인증·DB·큐·배포·프레임워크 변경을 추가하지 않는다.
8. 실제 입력으로 전체 흐름을 작게 먼저 연결하고 필수 요구사항을 완성한다. UI·보고서·스크립트 등 산출물 형태는 실제 요구에 맞춘다. 중간 최소 버전을 최종 완성으로 취급하지 않는다.
9. 실행한 것만 검증 완료로 기록한다. 기대값은 원문·원자료·수계산·독립 기준 등에서 얻는다. 구현을 복제한 검증이나 동일 코드 재호출만으로 계산의 정확성을 주장하지 않는다.
10. 같은 파일·설정·잠금 파일·공유 DB·서버 포트의 충돌을 피한다. 검증은 확인한 파일 상태·입력·명령·결과를 남기며 이후 수정으로 결과가 낡으면 영향 범위만 다시 확인한다.
11. 실무자 질문 후보는 누구나 찾되 T1이 중복·원문을 확인하고 사용자에게 제안한다. 실제 질문과 답변 전달은 사용자가 한다. 실무자에게 물을 업무 규칙과 코드에서 확인할 동작을 구분한다.
12. 중요한 결정·실패·검증 결과가 바뀔 때 짧게 보고한다. 의미 없는 상태 반복 조회·장문 보고·중복 분석·끝없는 리뷰를 하지 않는다. 필요한 후속 행동 하나를 명확히 한다.
13. 설명은 실제 구현·실제 검증·미검증·추후 개선을 구분한다. 사용자의 의도나 동의를 지어내지 않는다. 이해 연습은 사용자가 먼저 답하고 코드 근거로 확인하는 방식으로 한다.
14. 선택한 스킬만 필요할 때 읽는다. 역할 문서를 읽는 것과 스킬을 설치·등록하는 것은 다르다. 추가 플러그인·하네스·자동 통신 구축은 기본 절차가 아니다.
15. 허용 도구와 반입·외부 전송 규칙을 따른다. 시험 내용·실제 기록·제출물을 공개 저장소로 Push하거나 외부에 전송하지 않는다. AI 금지 단계로 전환되면 도구 실행·설명·파일 읽기를 포함한 AI 지원을 멈춘다.
