# 운영안 — 실제 작업량에 따라 선택

특정 과제·알고리즘·구현 구조를 정하는 문서가 아니다. 세션 수의 최적성을 보장하지 않는다.

| 운영안 | 사용할 상황 | 역할 |
| --- | --- | --- |
| B: 4세션 | 독립 구현량이 크고 별도 설명이 필요한 경우 | T1 정리·질문 / T2 구현 A / T3 구현 B / T4 설명 |
| A: 3세션 | 두 구현자는 필요하고 설명을 T1이 겸할 수 있는 경우 | T1 정리·질문·짧은 설명 / T2 구현 A / T3 구현 B |
| C: 2세션 | 한 구현자로 충분한 경우 | T1 정리·질문·설명 / T2 구현·검증 |

## 시작 조건

T1 핵심 파악 → T2 기술·작업 확인과 분리 제안 → 독립 범위 공유 후 T2·T3 병렬 진행 → 첫 결과부터 필요할 때 T4 설명.

T1의 전체 정리나 실무자 대화 완료를 기다리지 않는다. T2는 전체를 혼자 만든 뒤 T3에 넘기지 않는다. T1이 공유 분담을 취합하며 실제 전달은 사용자가 한다.

## 나눌 수 있는지 판단

- 담당 기능·파일과 입출력·실패 표현·완료 기준이 명확한가?
- 공통 파일·자원의 작성자가 정해져 있는가?
- 작업을 넘기면 실제 구현량이 줄고 일찍 연결할 수 있는가?

분리는 실제 작업량과 의존 관계로 정한다. 미리 정한 계층이나 기술로 고정하지 않는다. 같은 핵심 파일을 함께 고쳐야 한다면 한 명이 구현하고 다른 세션은 독립 검사·비교 기준 등으로 조정한다.

## 역할 경계

| 일 | 책임 |
| --- | --- |
| 원문 요구·출처·업무 질문·상태 | T1 |
| 담당 상세 분석·구현·검증·수정 | T2·T3 각각 |
| 전체 결과 연결 | 지정한 통합 담당, 기본 T2. 결함 수정은 각 파일 담당 |
| 핵심 계산·필수 조건 교차 확인 | T2·T3가 독립 근거로 나눠 수행 |
| 실제 결과·선택·한계 설명 | T4 또는 작은 운영안의 T1 |
| 중요 판단·실무자 소통·대표 결과 확인·제출 | 사용자 |

사용자가 세션 간 전달만 하게 되면 보고를 줄인다. 각 세션은 새 사실·중요 선택·충돌·연결 준비만 짧게 보고한다. 설명과 문서를 구현의 승인 단계로 만들지 않는다.

## 독립 세션 사용

기본은 같은 프로젝트에서 별도 Codex 세션을 실행해 역할 프롬프트를 주는 방식이다. 별도 터미널이나 이름만으로 역할·대화가 공유되지는 않는다. 제공 환경에서 허용된 서브에이전트를 사용할 수도 있지만 이를 필수 조건으로 삼거나 추가 설치·자동 통신을 구축하지 않는다.
