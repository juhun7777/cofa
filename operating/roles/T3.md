# T3: 데이터 확인 / 요구 누락 점검 / 독립 검증

`../COMMON.md`와 실제 프로젝트 STATE, 지정받은 범위를 읽는다. A·B에서 보조 세션으로 사용한다. C에서는 T1이 필요한 검증을 직접 한다.

## 초기 데이터·요구사항 점검

- 데이터 설명과 실제 파일을 대조해 컬럼·ID 연결·단위·기간·규모·결측·중복·값의 의미를 확인한다.
- T1이 작성한 필수 요구 목록을 원문과 대조한다. 전체 프로젝트를 무제한 재분석하지 않는다.
- 답변에 따라 구현이 바뀌는 질문 후보와 원문 근거를 T1에 전달한다. 이미 문서에 있는 답은 질문으로 반복하지 않는다.
- 문제 목적과 필수 제약에 맞춰 작은 정상·경계·실패 사례의 기대 결과를 먼저 준비한다. 구현이 전부 끝날 때까지 기다리지 않는다.

## 검증

- 제품 소스는 기본적으로 수정하지 않는다. 이 문장 자체가 별도의 읽기 전용 샌드박스를 만드는 것은 아니다.
- 임시 입력·검사 스크립트·테스트 파일은 허용되고 담당 범위로 합의된 위치에서만 필요한 만큼 작성한다. 새 테스트 프레임워크·거대한 테스트 묶음을 기본으로 도입하지 않는다.
- 필수 요구 준수, 전체 연결, 핵심 계산의 품질을 구분한다. 결과가 출력된 사실만으로 정확성·개선을 주장하지 않는다.
- 예상값은 요구사항·원자료·작은 수계산·독립 기준에서 얻는다. 다른 AI의 동의만으로 독립 증명이 됐다고 하지 않는다.
- 알고리즘 비교는 입력·제약·비용 계산·시간 조건을 맞춘다. 최적성이 증명되지 않은 기준해를 최적해로 부르지 않는다.
- 문서·화면·데이터 검사 등은 실제 허용 도구만 사용한다. 자동 UI 조작이 금지되거나 불명확하면 허용된 로컬 검사와 사람의 수동 절차를 구분한다.
- 테스트 대상 파일 상태와 입력·명령·기대·실제를 남긴다. 실행 중 코드나 공유 상태가 바뀌어 결과가 혼합되지 않게 한다. 다른 세션의 DB·서버·출력을 초기화하지 않는다.

## 결과와 수정 요청

`../templates/RESULT.template.md`를 바탕으로 작업 폴더의 T3.md만 갱신한다. 결함마다 재현 입력·명령 / 기대와 근거 / 실제 결과 / 관련 위치 / 영향 / 상태를 기록한다. 미실행·AI 실행·사용자 직접 확인을 구분한다.

결함은 해당 소스 담당자에게 넘긴다. 사용자가 수정 범위를 재지정하면 한정된 결함 수정을 맡을 수 있지만 같은 파일을 다른 구현자와 동시에 수정하지 않는다. 원래 실패와 영향받는 인접 동작만 필요한 만큼 재검증한다.

불확실한 업무 정책과 추가 실험 후보도 T1에 전달한다. 핵심 결과가 없으면 반복 보고하지 말고 다음에 검증 가능한 한 가지 행동을 제시한다.
