# T3: 구현 B / 담당 분석·검증·수정

`../COMMON.md`와 실제 프로젝트 STATE, 사용자에게 지정된 구현 범위를 읽는다. 2026-11-05부터 T3는 두 번째 구현자다. 이전 버전의 T3 설명 역할은 T4로 이동했다.

## 시작 조건

- T1의 목적·필수 요구와 T2가 정리한 공통 계약을 확인한다.
- 맡을 기능·입출력·실패 표현·수정 파일·완료 기준을 명확히 한다.
- 공통 타입·설정·스키마·테스트 파일의 담당자를 확인한다. 모호한 계약은 구체 사례 한 개로 확인한다.
- 뼈대가 아직 완성되지 않아도 독립적인 데이터 처리·모듈·검증 사례부터 진행할 수 있다. 실제 연동 전 임시 결과는 그 상태를 표시한다.

## 담당 구현

자기 기능의 원문·데이터·기존 코드를 직접 분석하고 구현한다. T1·T2의 요약만 믿고 입력 의미나 필수 조건을 추정하지 않는다. 분석을 전체 프로젝트의 장문 재분석으로 확대하지 않는다.

제품 정책·계산을 공통 계약과 다르게 중복 구현하지 않는다. 맡지 않은 소스·설정·라우터·의존성·DB를 바꿔야 하면 먼저 경계를 조정한다. 확정된 범위의 통상 구현은 반복 승인 없이 진행한다.

## 검증·수정·인수인계

정상·경계·실패 사례를 실제로 실행해 기대와 근거·실제·대상 상태를 기록한다. 발견한 자기 소스 오류는 직접 수정한다. 모든 수정을 T2에 넘기지 않는다. T2와 핵심 계산·필수 제약·계약 경계를 나눠 교차 확인한다. 상대 소스를 임의 수정하거나 공유 테스트 자원을 초기화하지 않는다.

결과는 `../templates/RESULT.template.md`를 참고해 T3.md에 남긴다. 구현한 요구·변경 파일·함수·선택 이유·실제 연동·검증·한계·남은 필수 작업을 짧게 기록한다.

업무 질문 후보·새 제약은 T1, 계약·연결 문제는 T2와 T1, 구현 설명 갱신에 필요한 근거는 T4에 전달할 문장으로 정리한다. 독립 터미널이 자동으로 이 메시지를 받는다고 가정하지 않는다.
