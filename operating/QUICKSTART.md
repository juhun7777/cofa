# 빠른 시작 — 정리 T1 / 구현 T2·T3 / 설명 T4

2026-11-05 역할 개정. T1이 제품 코딩까지 맡기 어려운 상황을 반영했다. 이전 T1 구현·T3 설명 지침과 섞지 않는다. 실제 과제·규칙·환경이 우선이다.

## 현재 구성

| 역할 | 담당 |
| --- | --- |
| T1 | 단계별 문서·데이터 이해, 핵심·출처 표, 질문·답변·변경·요구 상태 관리 |
| T2 | 주 구현 A, 지정된 뼈대·공통 계약·기술 통합, 자기 분석·검증·수정 |
| T3 | 독립 구현 B, 자기 분석·검증·수정, T2와 교차 확인 |
| T4 | 실제 구현의 위치·흐름·원리·확인된 선택 이유·기존 검증·한계 설명 |

복잡한 과제는 B 4세션을 검토한다. 별도 설명 담당이 부담이면 A 3세션에서 T1이 설명을 겸한다. 한 구현자로 충분한 작은 과제는 C 2세션이다. 세션 수 자체가 목표는 아니다.

## 1. 준비 자료 받기 — 일반 셸

공개 저장소 다운로드가 허용되고 Git이 제공될 때 실제 프로젝트 루트의 터미널에서 실행한다.

```sh
git clone --depth 1 https://github.com/juhun7777/cofa.git cofa-prep
```

이 명령이 cofa-prep 폴더를 자동 생성한다. 미리 만들거나 세션마다 다시 내려받을 필요는 없다. 이미 내용이 있는 폴더에 덮어쓰지 않는다. ZIP이면 허용된 위치의 cofa-prep로 압축 해제한다. 막혀 있으면 안내를 따르며 우회·추가 설치를 하지 않는다.

```text
실제 프로젝트/
  README·데이터·기존 소스
  cofa-prep/operating/        ← 준비 지침
    COMMON.md, MODES.md, QUESTIONS.md
    roles/T1.md, T2.md, T3.md, T4.md
    templates/
  _work/                     ← 허용될 때의 실제 기록, 경로 변경 가능
    STATE.md                 ← T1
    T2.md                    ← T2
    T3.md                    ← T3
    UNDERSTANDING.md         ← T4, 또는 A/C의 T1
```

실제 문제·데이터·작업 기록은 준비 저장소 안에 쓰거나 공개 Push하지 않는다. 원본 지침과 충돌하는 작업 폴더는 만들지 않는다.

## 2. 실제 프로젝트에서 Codex 실행

시험이 제공한 실행 방법을 사용한다. codex 명령이 제공되는 경우:

```sh
codex
```

새 터미널도 같은 실제 프로젝트 루트인지 확인한다. 아래 문장은 Codex 실행 후 대화 입력창에 넣는 프롬프트이며 셸 명령이 아니다. 준비 폴더를 실제 앱 루트로 취급하지 않는다.

## 3. T1 시작

아래 주요 경로 세 개는 예시다. 시험 시작 후 탐색기에서 확인한 실제 경로로 바꿔 넣는다. 상대 경로는 실제 프로젝트 루트를 기준으로 한다.

```text
현재는 AI 허용 과제 단계다. 시간은 내가 관리한다.
현재 작업 폴더가 실제 시험 프로젝트 루트인지 먼저 확인해 줘.
과제·규칙·실행·제출 안내를 직접 찾아 읽고 실제 경로와 출처를 기록해 줘.
작업 폴더가 잘못됐거나 안내만으로 확인할 수 없는 중요 조건은 알려 줘.

참고할 주요 경로:
- 과제 README: ./README.md
- 데이터 설명: ./data/README.md
- 실제 데이터: ./data/

실제로 존재하는 경로와 내용을 확인하고,
관련된 추가 지침도 찾아 읽어 줘.
cofa-prep는 준비 자료이므로 실제 과제·데이터와 구분해 줘.

너는 T1 프로젝트 이해·정리·질문 담당이다.
cofa-prep/operating/COMMON.md와 cofa-prep/operating/roles/T1.md를 읽어 줘.
cofa-prep/operating/MODES.md를 참고해 작업량에 맞는 구성을 제안해 줘.

관련 파일 목록을 확인하고 초기 읽기를 세 단계로 나눠 진행해 줘.
1. 과제 README·제약·금지·실행·제출 지침
2. 데이터 설명과 실제 컬럼·단위·대표 행·규모·ID·중요한 결측/중복
3. 관련 기존 코드·실행 진입점·재사용 가능한 부분
긴 문서는 절 단위로 읽고 미확인 범위를 표시해 줘.
중요한 판단이 필요하지 않으면 단계마다 승인을 기다리지 말고 계속해 줘.

내용 / 무엇을 뜻하고 왜 핵심인지 / 출처(파일·절·줄) /
확정·추정·미확인 / 구현·검증 영향 / 다음 질문을 표로 정리해 줘.
목적·필수 조건·성공 기준을 내가 함께 이해할 수 있게 해 줘.

제품 구현은 T2·T3가 나누도록 업무 범위·우선순위를 정리하고,
구현자가 파일·입출력·실패 표현·완료 기준을 맞추게 해 줘.
중요한 실무자 질문과 실제 답변의 변경 영향을 계속 관리해 줘.
모든 README·데이터 확인이 끝날 때까지 질문을 미루지 마.
관련 원문에 답이 있는지 먼저 확인하고, 아래 시점에 필요한 질문을 제시해 줘.
- 초기 요구 파악: 목적·필수 기능·성공 기준·우선순위
- 데이터 확인: 컬럼·단위·ID·누락/중복·설명과 실제 데이터의 불일치
- 구현·검증: 실패/부분 성공·예외·실제 업무 적용 기준
확인한 사실·미확인·답에 따라 달라질 구현/검증을 붙여 중요한 질문 1~3개부터 제시해 줘.
답변을 기다리는 동안 영향받지 않는 작업은 계속하고 미확인 정책은 임의 확정하지 마.
새 정보 없는 재요약과 사소한 작업의 반복 승인은 하지 마.

실제 기록은 프로젝트 루트의 _work/STATE.md에 취합해 줘.
시험 지침에서 허용하는 경우 _work 폴더와 STATE.md가 없으면 생성하고,
cofa-prep/operating/templates/STATE.template.md를 참고해 작성해 줘.
이미 STATE.md가 있다면 기존 내용을 읽고 필요한 부분만 갱신해 줘.
STATE.md의 작성·갱신은 T1만 담당하고 다른 세션은 읽어서 활용하게 해 줘.
원본 README와 데이터 설명은 덮어쓰지 마.
기술 분리 초안을 받으면 STATE에 공유 작업약속 ID를 붙여
두 구현자에게 같은 범위·입출력·실패·완료 기준을 전달해 줘.
T1의 전체 정리·실무자 대화나 T2의 전체 뼈대 완료를 기다리지 말고,
독립 기능·파일·입출력·실패 표현·완료 기준이 정해지면
T3가 지금 시작할 범위와 사용자에게 전달할 시작 문장을 만들어 줘.
미확인 정책에 영향을 받는 부분만 구분하고 확정 범위는 진행하게 해 줘.
```

## 4. T2 주 구현 시작

T1의 핵심 요구가 파악되고 기술 확인을 맡길 범위가 있으면 시작한다. 모든 상세 정리가 끝날 때까지 기다리지 않는다.

```text
너는 현재 시험 프로젝트의 T2 주 구현 A 담당이다.
cofa-prep/operating/COMMON.md와 cofa-prep/operating/roles/T2.md,
_work/STATE.md의 최신 목적·제약·우선순위를 읽어 줘.

우선 초기 기술 확인과 T2·T3 구현 분리 초안을 맡아 줘.
T1의 전체 정리·실무자 답변이나 전체 뼈대 완성을 기다리지 말고,
T3의 독립 범위가 정해지면 먼저 공유할 수 있게 해 줘.
제공 스택을 확인하고 작은 뼈대와 실제 입력의 전체 흐름을 계획해 줘.
T3와 나눌 기능·수정/금지 파일·입출력 예시·실패/부분 성공·완료 기준,
공통 타입·설정·스키마·테스트 자원 담당자를 제안해 줘.
기록 폴더가 허용되면 _work/T2.md가 없을 때 생성해 초안을 남겨 줘.
STATE.md는 수정하지 말고 T1에게 전달할 짧은 문장을 만들어 줘.
제품 파일 수정 전 같은 약속 ID와 자기/상대 범위를 읽고 짧게 확인해 줘.
자기 부분의 분석·구현·검증·오류 수정을 맡고 모든 코드를 혼자 작성하지 마.
결과·중요 선택 이유·변경 함수·검증 근거를 _work/T2.md에 남겨 줘.
```

## 5. T3 두 번째 구현 시작

```text
너는 현재 시험 프로젝트의 T3 구현 B 담당이다.
cofa-prep/operating/COMMON.md와 cofa-prep/operating/roles/T3.md,
_work/STATE.md와 관련 _work/T2.md를 읽어 줘.

STATE에서 공유 상태인 최신 작업약속 ID를 읽고 보고해 줘.
아직 공유 범위가 없다면 지정할 기능과 파일을 확인하고 임의로 소스를 수정하지 마.
자기 기능·수정/금지 파일·상대 담당·공통 파일 작성자,
입출력 예시·실패/부분 성공·실제 완료 기준을 먼저 짧게 확인해 줘.
누락·겹침·충돌이 있는 부분은 쓰지 말고 확인해 줘.
공유된 독립 범위가 확인되면 T1의 전체 정리·실무자 대화나
T2의 전체 뼈대 완성을 기다리지 말고 시작해 줘.
미확인 정책에 의존하는 부분만 보류하고 확정된 범위는 진행해 줘.
담당 부분의 상세 분석·구현·정상/경계/실패 검증·수정을 수행해 줘.
T2 담당과 공통 설정은 임의 수정하지 마. 실제 연결은 일찍 확인해 줘.
중요한 계산·필수 조건·경계는 T2와 나눠 교차 확인해 줘.
기록 폴더가 허용되면 _work/T3.md가 없을 때 생성하고,
결과·선택 이유·변경 함수·검증 근거를 남겨 줘.
```

## 6. T4 구현 설명 시작 — 별도 설명 담당이 필요할 때

```text
너는 현재 시험 프로젝트의 T4 구현 설명 담당이다.
cofa-prep/operating/COMMON.md와 cofa-prep/operating/roles/T4.md,
_work/STATE.md·_work/T2.md·_work/T3.md의 관련 기록과 실제 코드를 읽어 줘.

무엇을 만들었고 어디에 있으며 어떻게 동작하는지,
핵심 원리·확인된 선택 이유·대안·한계·기존 검증을 설명해 줘.
기록에 없는 의도는 지어내지 말고 확인 질문으로 남겨 줘.
기록 폴더가 허용되면 _work/UNDERSTANDING.md가 없을 때 생성하고,
cofa-prep/operating/templates/UNDERSTANDING.template.md를 참고해
그 파일 하나에 설명을 정리해 줘.
첫 기능·모듈·작은 전체 흐름이 생기면 설명을 시작하고,
의미 있는 기능 추가·핵심 방식 변경·연결 변경·중요 검증 결과가
전달될 때 해당 부분만 갱신해 줘. 사소한 수정마다 전체를 다시 쓰지 마.
전체 구현 완료까지 기다리거나 설명 확인을 구현 진행의 승인으로 삼지 마.
제품 소스·다른 기록을 수정하거나 전체 테스트를 떠맡지 마.
```

처음에는 목적·조건·모듈 개요, 구현 후에는 실제 처리와 근거를 설명한다. T1의 요구·상태 표와 T4의 상세 구현 설명을 중복 복제하지 않는다.

## 7. 변경·질문·통합 전달

- 실무자 답변 → T1: 실제 답변을 전달하고 확정 조건·남은 가정·바뀌는 요구/구현/검증을 STATE에 갱신하게 한다.
- T1 → T2·T3: 읽을 STATE 위치와 새 정책·완료 조건만 짧게 전달한다.
- T2↔T3: 공통 계약·변경 파일·재현 결함·연결 결과를 지정 기록에 남기고 읽을 위치를 전달한다.
- T2·T3 → T4: 새 기능·파일·핵심 함수·확인된 선택 이유·기존 검증 위치를 전달한다.
- T4 → T1 또는 구현자: 이유 누락·코드 모순을 근거 위치와 함께 확인 요청한다.

독립 세션이 자동으로 메시지·파일 변경을 읽는 것은 아니다. 중요한 변경 때 사용자가 짧게 전달한다. 한시 독립 검사가 필요하면 구체 범위를 배정하되 모든 검증·수정을 T1 또는 T2로 몰지 않는다.

## 8. Markdown 지침과 사용 범위

준비 지침은 operating/ 안에 모두 있다. COMMON.md와 담당 역할 파일을 실제로 읽으라는 프롬프트로 사용한다. 별도 등록·설치나 새 AGENTS.md 생성은 필요 없다. 기존 시험 지침을 덮어쓰지 않는다. ZIP에는 README와 operating/만 포함된다.

실제 도구·자료 반입·외부 전송·후속 단계 규칙을 따른다. AI 금지 단계에서는 설명·파일 읽기도 중단한다. 공식 참고: https://learn.chatgpt.com/docs/agent-configuration/agents-md 및 https://learn.chatgpt.com/docs/agent-configuration/subagents

## 9. 시험 시작 직후부터 제출까지 — 사용자 실행 시뮬레이션

실제 시험에서 사용자가 무엇을 열고, 어디에 어떤 문장을 넣고, 어떤 결과를 확인할지 순서대로 정리했다. 과제 내용은 시작 후 확인한다. 아래 예시는 정답이나 정해진 구현 구조가 아니다. 시간 관리는 사용자가 하며 남은 시간을 파일에 입력하지 않는다.

### 9-1. 첫 화면: 원본 안내와 프로젝트 위치 확인

1. 왼쪽 파일 탐색기에서 과제 README, 데이터 폴더, 기존 소스가 있는 프로젝트를 확인한다.
2. 과제 README와 시험 안내에서 외부 자료 반입·GitHub 다운로드·작업 폴더·제출 방법을 먼저 확인한다.
3. 일반 터미널을 연다. 명령 프롬프트의 현재 경로가 실제 프로젝트인지 확인한다. 필요하면 제공 셸의 `pwd` 명령으로 위치를 확인한다.
4. 잘못된 위치라면 실제 경로로 이동한다. 파일 탐색기에서 폴더를 클릭하는 것만으로 이미 열린 터미널의 작업 경로가 바뀐다고 가정하지 않는다.

경로에 공백이 있으면 이동할 경로를 따옴표로 감싼다. 프로젝트 폴더명과 경로는 실제 화면에서 확인하며 예시 경로를 그대로 입력하지 않는다.

### 9-2. 준비 자료 다운로드: 일반 터미널에서 한 번

```sh
git clone --depth 1 https://github.com/juhun7777/cofa.git cofa-prep
```

실행 후 탐색기에 `cofa-prep/operating/`이 생기는지 확인한다. 폴더를 미리 만들거나 세션마다 clone하지 않는다. 이미 자료가 있다면 내용부터 확인한다. 준비 폴더로 `cd`하지 않고 실제 프로젝트 루트에 머문다.

사용할 파일은 다음과 같다.

| 위치 | 누가 사용하는가 | 용도 |
| --- | --- | --- |
| cofa-prep/operating/QUICKSTART.md | 사용자 | 시작 프롬프트와 이 진행 순서 |
| cofa-prep/operating/COMMON.md | 모든 세션 | 공통 원칙 |
| cofa-prep/operating/roles/T1.md 등 | 해당 세션 | 역할·작업 경계 |
| cofa-prep/operating/templates/ | 해당 기록 작성자 | 빈 기록 양식 |
| 프로젝트 루트의 _work/ | 모든 세션이 읽고 각 담당자가 작성 | 현재 시험에서 확인·구현·검증한 기록 |

원본 README, 데이터 README, STATE.md는 서로 다른 파일이다. 원본은 요구의 출처이고 STATE는 현재 이해·질문·변경·상태를 추적하는 기록이다.

### 9-3. T1 시작: 전체를 기다리지 말고 핵심부터 확인

실제 프로젝트 루트에서 제공된 Codex를 실행하고 이 문서 3절의 T1 시작 프롬프트를 붙여넣는다. 제공 환경에서 평소 사용할 모델·추론 설정을 선택한다. 이 문서 때문에 설치·업데이트를 할 필요는 없다.

이때부터 입력하는 역할 문장은 셸 명령이 아니라 Codex 대화 입력이다. T1은 허용된 경우 `_work/STATE.md`를 직접 만들며 사용자가 빈 파일을 미리 준비할 필요는 없다.

T1이 읽기를 진행하는 동안 사용자는 원본 README의 목적·필수 조건·제출 조건을 확인한다. 첫 보고에서 아래를 점검한다.

| 사용자가 이해해야 할 것 | T1이 제시할 근거 |
| --- | --- |
| 누가 무엇을 하려고 하는 서비스·결과물인가 | 업무 목적·사용자·산출물의 출처 |
| 무엇을 입력받아 어떤 결과를 내야 하는가 | 입력→처리→출력과 실제 데이터 예시 |
| 반드시 지켜야 할 것은 무엇인가 | 요구 ID·필수 제약·원문 위치 |
| 무엇이면 성공이라고 볼 것인가 | 실행하거나 대조할 수 있는 완료 조건 |
| 아직 무엇을 모르는가 | 미확인 내용·구현 영향·우선 질문 |

긴 문서 전체의 완성된 요약을 기다리지 않는다. 핵심 요구와 초기 기술 확인 범위가 생기면 T2를 시작한다. T1은 남은 자료와 업무 질문을 계속 정리한다.

### 9-4. 실무자 질문: 사용자가 묻고 실제 답변을 T1에 전달

모든 README와 데이터 확인이 끝날 때까지 질문을 미루지 않는다. 관련 원문에서 답을 먼저 찾되, 구현 방향·필수 조건·성공 기준에 영향을 주는 미확인이 나오면 해당 시점에 중요한 질문 1~3개부터 사용자에게 제시한다. 아래 시점은 질문을 세 번만 하라는 뜻이 아니며 실제 정보가 생길 때 적용한다.

| 시점 | 확인하고 질문할 내용 |
| --- | --- |
| 초기 요구사항 파악 중 | 업무 목적, 필수 기능, 성공 기준, 구현 방향을 바꾸는 우선순위 |
| 데이터 확인 중 | 컬럼·단위·ID의 의미, 누락·중복 처리, README와 실제 데이터의 불일치 |
| 구현·검증 중 | 실패·부분 성공 정책, 예외 상황, 결과를 실제 업무에 적용할 기준 |

질문마다 관련 원문·데이터에서 확인한 사실, 아직 모르는 부분, 답에 따라 달라질 구현·검증을 짧게 붙인다. 답을 기다리는 동안 영향받지 않는 분석·구현·검증 준비는 계속한다. 답이 필요한 부분은 미확인 상태를 표시하고 업무 정책을 임의로 확정하지 않는다. 질문 내용이 기술 선택·코드 동작이면 실무자 대신 관련 구현자와 코드·실행에서 확인한다.

T1이 제안한 질문을 사용자가 실무자 창에 보내고 실제 답변을 T1에 전달한다.

예를 들어 일부 입력만 처리 가능한 상황이 있다면 다음처럼 결과 정책을 구체적으로 묻는다.

> 일부 입력을 처리하지 못했을 때 가능한 결과만 제공해도 되나요? 전체 요청을 실패로 처리해야 한다면 기존 정상 결과는 유지해야 하나요?

답이 모호하면 선택지를 좁혀 재질문한다. 기능이 명확해졌다면 질문을 위한 질문을 늘리지 않는다. 받은 실제 답변은 T1에 다음처럼 전달한다.

```text
실무자에게 받은 실제 답변이야.
[실제 답변 붙여넣기]

확정된 조건·남은 가정·미확인을 구분하고 STATE에 갱신해 줘.
바뀌는 요구·구현·검증과 담당자를 짚어 줘.
관련 세션에 전달할 짧은 문장도 만들어 줘.
```

### 9-5. T2 시작: 기술 확인과 두 구현자의 분리 초안

새 터미널을 열어 같은 실제 프로젝트 루트인지 확인하고 별도의 Codex 세션을 실행한다. 사용자 구분용으로 터미널 이름을 T2로 바꿀 수 있다. 이 이름이 AI에 자동 역할을 부여하는 것은 아니므로 4절의 T2 프롬프트를 입력한다.

T2는 STATE의 핵심 요구와 실제 기존 코드를 확인하고 `_work/T2.md`에 분리 초안을 남긴다. 아직 전체 문서 분석이 끝나지 않아도 수행할 수 있다. 사용자는 전체 기술 명세를 직접 작성할 필요는 없지만 나눈 범위가 필수 기능과 연결되는지 확인한다.

여기서 **기존 코드·실행 구조 확인**은 이미 제공된 기능과 실행 경로를 찾아 재사용 범위와 실제 구현할 부분을 정하는 작업이다. 전체 코드를 정독하거나 새 구조를 만드는 작업이 아니다.

| 확인할 것 | T2가 찾을 내용 | 이유 |
| --- | --- | --- |
| 실행 방법 | README의 시작·검사 명령과 제공 설정 | 어떤 명령으로 현재 프로젝트를 실행하는지 알기 위해 |
| 시작 파일·호출 흐름 | 입력을 받는 파일에서 핵심 처리·결과로 이어지는 경로 | 기능을 어디에 연결할지 정하기 위해 |
| 이미 제공된 기능 | 데이터 읽기·화면·저장·핵심 함수 중 실제 구현된 부분 | 필요한 기존 코드를 재사용하고 중복 작성을 피하기 위해 |
| 아직 없는 기능 | 빈 함수·TODO·임시 고정 결과·요구와 다른 부분 | 실제 구현할 범위를 정하기 위해 |
| 현재 실행 상태 | 안내된 안전한 범위의 실행 결과와 기존 오류 | 기존 문제와 변경 후 문제를 구분하기 위해 |

예를 들어 화면과 입력 처리는 제공됐지만 계산 함수가 비어 있다면, 기존 화면을 활용하고 계산·결과 연결을 나눈다. 코드가 없고 데이터만 있으면 그 사실을 확인한 뒤 필요한 최소 진입점과 기능을 계획한다. 화면·서버·DB가 있다고 가정하지 않는다.

T2는 결과를 장문 분석서 대신 **실행 방법 / 관련 파일·함수 / 재사용 가능 / 미구현·기존 오류 / 작업 분리 제안**으로 짧게 남긴다. 다른 세션이 사용 중인 DB·서버·공유 데이터를 초기화하지 않는다.

가상의 데이터 처리 서비스라면 다음처럼 나눌 수 있다. 실제 과제의 기존 구조를 우선하며 이 디렉터리를 무조건 만들지 않는다.

| 항목 | T2 예시 | T3 예시 |
| --- | --- | --- |
| 기능 | 요청·조회·필요한 저장·연결 | 핵심 계산·결과 조건 검사 |
| 수정 범위 | 지정 API·화면·저장 파일·담당 테스트 | 지정 계산 모듈·담당 테스트 |
| 수정 금지 | T3 계산 모듈·테스트 | T2 파일·공통 설정 |
| 공통 파일 | 지정 타입·설정의 단일 작성자 | 읽어서 사용, 변경은 요청 |
| 완료 확인 | 작은 실제 입력의 요청→결과→필요한 조회 흐름 | 정상·경계·실패 사례를 독립 기대값과 비교 |

함수 입력·출력은 실제 데이터의 필드·단위·ID와 맞춰 작은 예시를 정한다. 실패·부분 성공에 대해서도 허용 조건과 표현을 함께 정한다. 해결할 수 없는 입력인데 정상 성공처럼 보이는 값을 반환하지 않도록 한다.

### 9-6. T1에 분리 초안 취합 요청

T2의 초안이 준비되면 T1 대화창에 보낸다.

```text
_work/T2.md의 구현 분리 초안을 읽어 줘.
업무 요구·실제 데이터·완료 조건과 충돌하는 부분을 확인하고,
STATE의 작업 경계에 공유 작업약속 W1로 취합해 줘.

각자의 담당 기능·수정/금지 파일, 실제 입출력 예시,
실패·부분 성공 표현, 실제 완료 기준,
공통 타입·설정·스키마·서버·테스트 자원 담당자를 명시해 줘.

불필요한 공통 자원은 만들지 마.
T2·T3에 각각 전달할 짧은 시작 문장을 만들어 줘.
```

W1은 같은 분담표를 읽는지 확인하는 표시다. 모든 분석·모든 파일의 완성을 기다리는 승인 단계가 아니다. 독립 기능의 경계가 확정되면 그 범위부터 공유할 수 있다. 기술적 모순은 해당 구현자에게 수정안을 받으며 T1이 임의로 기술 사실을 확정하지 않는다.

### 9-7. T2·T3 병렬 구현 시작

T3 시작의 기준은 전체 정리 완료가 아니라 겹치지 않는 독립 작업 범위의 확정이다. T1의 나머지 데이터 분석·실무자 대화나 T2의 전체 뼈대 완성을 기다리지 않는다.

T2에 다음 문장을 보내고, 새 터미널의 T3에는 5절의 시작 프롬프트를 입력한다. 두 세션이 같은 공유 작업약속 ID를 읽었는지 짧게 확인한다.

```text
_work/STATE.md의 공유 작업약속 W1을 읽어 줘.
자기 담당·수정/금지 파일·상대 범위·공통 파일 담당자,
입출력·실패/부분 성공·실제 완료 기준을 짧게 확인해 줘.
확인 내용은 자기 기록에 남기고 STATE.md는 수정하지 마.

겹치거나 불명확한 부분의 쓰기는 보류하고 확인해 줘.
정해진 독립 범위는 전체 뼈대 완성을 기다리지 않고 구현해 줘.
자기 분석·구현·검증·수정을 수행하고 작은 실제 데이터로 일찍 연결해 줘.
```

T3가 맡을 파일이 없거나 같은 핵심 함수를 함께 고쳐야 한다면 억지로 두 명이 수정하지 않는다. 한 명이 소스를 맡고 다른 세션은 작은 독립 계산·실패 사례·비교 기준을 맡도록 경계를 조정한다.

T2가 아직 서버나 화면을 연결하는 중이어도 T3는 합의한 입출력으로 계산 모듈을 구현할 수 있다. 대체 입력으로만 확인한 결과는 임시 상태로 기록하고, 실제 데이터 연결을 별도로 확인한다.

### 9-8. 작업 중 사용자가 전달할 것은 중요한 변경

독립 세션은 상대 대화와 최신 파일을 자동으로 읽지 않는다. 모든 도구 출력과 대화를 복사하지 말고 바뀐 경로·내용·필요한 행동만 전달한다.

| 발생한 일 | 전달할 세션 | 짧은 전달 예시 |
| --- | --- | --- |
| 실무자 답변으로 정책 변경 | 먼저 T1, 이후 영향받는 구현자 | STATE의 변경 조건과 W2를 읽고 자기 부분에 반영해 줘. |
| T3 모듈 연결 준비 완료 | T2 | T3.md의 입출력·검증 결과를 읽고 작은 실제 입력으로 연결해 줘. |
| 상대 소스에서 오류 발견 | 해당 소스 담당자 | 기록에 적은 재현 입력·기대·실제 결과를 보고 자기 소스를 수정·재검증해 줘. |
| 공통 타입·스키마 변경 필요 | T1과 공통 파일 담당자 | 필요한 변경·영향·상대 호출부를 확인하고 경계를 맞춘 뒤 반영해 줘. |
| 기능이나 알고리즘이 크게 변경 | T4 | 변경된 파일·함수와 결정·검증 기록을 읽고 설명의 해당 부분을 갱신해 줘. |

파일 경계와 계약이 바뀌면 T1이 W2처럼 갱신하고 영향받는 세션이 읽도록 전달한다. 단순 설명 문구나 상태 갱신마다 ID를 바꿀 필요는 없다. 문제없는 독립 작업까지 멈추거나 사소한 수정마다 승인을 받지 않는다.

### 9-9. 코드가 생기면 T4 시작: 본인이 설명할 수 있는지 확인

별도 설명 담당이 필요하면 네 번째 터미널에서 6절의 T4 프롬프트를 입력한다. 초기 문서를 처음부터 재분석시키기보다 실제 코드·선택·검증 근거를 보게 한다. T4는 허용된 경우 `_work/UNDERSTANDING.md`를 생성하고 그 파일만 관리한다.

T4는 전체 완성 후에만 부르는 역할이 아니다. 첫 기능·모듈·작은 실제 흐름이 생기면 시작하고 다음 시점에 필요한 부분을 갱신한다.

| 시점 | T4에 요청할 내용 |
| --- | --- |
| 첫 기능 또는 작은 흐름 동작 | 실제 입력→함수→결과, 구현된 부분·아직 연결되지 않은 부분 |
| 의미 있는 기능 묶음 추가 | 새 기능과 기존 흐름의 연결, 관련 파일·함수·선택 이유 |
| 알고리즘·업무 정책 변경 | 변경 근거, 대안·절충점, 이전 설명에서 바뀔 부분 |
| 중요 검증 결과·한계 발견 | 실제 확인한 결과, 미검증·실패 조건, 추가 검증 필요 |
| 최종 제출 전 | 최종 코드와 설명 일치, 구현·검증·한계의 최종 구분 |

사소한 수정마다 전체를 다시 설명시키지 않는다. 사용자가 모르는 부분은 언제든 물어볼 수 있다. T4 설명을 기다리느라 T2·T3의 독립 구현을 멈추지 않는다.

기능 갱신 때 쓸 짧은 전달 문장:

```text
T2.md와 T3.md의 최신 변경·선택·검증 기록을 읽고,
실제 변경된 파일·함수를 확인해 줘.
이번 기능의 목적·처리 흐름·원리·선택 이유·검증·한계를 설명하고,
UNDERSTANDING.md에서 영향받는 부분만 갱신해 줘.
기록에 없는 의도나 실행하지 않은 검증은 지어내지 마.
```

사용자는 중요한 구현 변경이 생겼을 때 다음처럼 구체적으로 질문할 수 있다.

```text
현재 구현에서 실제 입력 한 건을 골라,
어느 파일·함수를 지나 어떤 결과가 되는지 설명해 줘.
저장 단계가 있다면 무엇을 언제 어디에 저장하는지 포함해 줘.

핵심 방식의 선택 이유·검토한 대안·한계는 실제 기록에 근거해 설명하고,
확인되지 않은 의도는 질문으로 남겨 줘.
실제로 검증한 내용과 추가 검증이 필요한 내용을 구분해 줘.
```

설명을 읽고 사용자가 다시 자기 말로 처리 흐름·선택·한계를 설명해 본다. 이해하지 못한 용어·함수·검증 근거를 좁혀 질문한다. T4의 설명만으로 검증이 끝났다고 판단하지 않는다. 세 세션 운영이면 T1이 필요한 수준의 짧은 설명을 겸한다.

### 9-10. 구현·검증: 각자 검사하고 작은 전체 흐름 연결

T2·T3는 자기 범위에서 정상·경계·실패 사례를 실행하고 직접 수정한다. 핵심 계산과 필수 조건은 원문·원자료·수계산·독립 기준으로 범위를 나눠 교차 확인한다. 작은 실제 입력의 전체 흐름은 모든 기능 완성 전에 연결한다.

사용자가 연결 확인을 요청할 때 쓸 문장:

```text
합의한 작은 실제 입력으로 입력→핵심 처리→필요한 저장·출력의
전체 흐름을 실제 실행해 줘. 입력·기대와 그 근거·실제 결과를 남겨 줘.
연결 오류는 소스 담당자가 수정하고 관련 흐름을 다시 확인해 줘.
목업만 작동한 부분과 실제 연동을 구분해 줘.
```

T1에는 관련 기록을 읽고 요구별 구현 위치·검증 근거·미검증을 대조하게 한다. T1이 모든 테스트를 다시 돌릴 필요는 없다. 사용자는 중요한 기능을 직접 사용하고, 계산이나 판단 결과는 대표 사례 한 개라도 근거와 비교한다.

### 9-11. 사용자가 마무리 전환 지시

시간은 사용자가 보고 판단한다. 숫자 시간을 기록할 필요 없이 관련 세션에 다음처럼 보낸다.

```text
이제 선택 기능 추가를 멈추고 필수 누락·오류·실행·제출 확인을 우선해 줘.
새 구조 확장보다 현재 필수 흐름의 완성을 우선해 줘.
실제 완료·부분 충족·미검증·미구현을 구분하고,
필요한 수정과 재검증은 소스 담당자가 수행해 줘.
```

| 담당 | 마무리에 할 일 |
| --- | --- |
| T1 | 원문 요구·제약과 구현·증거 대조, 남은 필수 누락·제출 조건 정리 |
| T2 | 자기 부분·공통 연결·실행 경로 확인, 담당 결함 수정·재검증 |
| T3 | 자기 부분·핵심 조건 확인, 담당 결함 수정·재검증 |
| T4 | 최종 코드와 설명 일치, 실제 검증·한계·추가 검증 필요 구분 |
| 사용자 | 핵심 기능 직접 실행, 최종 선택·한계 이해, 지시된 방식으로 제출하고 반영 확인 |

제출 대상은 시험 안내가 정한다. 준비 폴더·작업 기록을 임의로 필수 제출물에 포함시키거나 원본 파일을 삭제하지 않는다. 저장되지 않은 변경이 없는지 확인하고 실제 제출·완료 표시를 직접 확인한다. AI 세션이 완료했다고 말한 것과 제출이 완료된 것은 별개다.

### 9-12. 후속 단계 전환

후속 단계의 AI·자료 열람 규칙을 따른다. 금지 단계라면 진행 중인 AI 작업·설명·파일 읽기도 중단한다. 기록을 열 수 있다고 미리 가정하지 않는다. 구체 질문이나 정답을 예측해 외우기보다 실제 선택·동작·검증·한계를 이해한 상태로 전환한다.

### 막혔을 때의 짧은 대응

| 상황 | 사용자가 할 일 |
| --- | --- |
| clone 경로가 잘못됨 | 현재 위치와 생성된 준비 폴더를 확인한다. 무작정 다시 clone하거나 삭제하지 말고 실제 자료 위치를 역할 프롬프트에 알려 준다. |
| clone 또는 Codex 실행이 막힘 | 제공 안내·지원 경로를 확인한다. 기존 준비 자료가 허용된 위치에 있으면 활용하고 설치·우회로 시간을 쓰지 않는다. |
| STATE.md가 없음 | T1에 허용된 _work/STATE.md를 양식 참고로 생성하라고 요청한다. |
| T2·T3가 같은 파일을 수정하려 함 | 해당 파일의 추가 쓰기를 멈추고 담당자 한 명을 정한다. 변경을 확인한 뒤 조정하며 상대 변경을 무작정 되돌리지 않는다. |
| 한 구현자가 상대 뼈대를 기다림 | 입출력과 독립 파일을 확정하고 모듈·대표 입력·실패 사례부터 진행하게 한다. |
| 세션이 과거 요구를 사용함 | 읽을 STATE 변경 위치와 작업약속 ID를 전달하고 영향받는 부분을 다시 확인하게 한다. |
| 문서 작성이 구현보다 커짐 | 새 사실·변경·필수 근거만 남기게 하고 중복 요약·문서 확장을 멈춘다. |
| 설명은 되지만 실행 근거가 없음 | 미검증으로 표시하고 해당 구현자에게 구체 입력·기대·실제 결과의 확인을 요청한다. |

사용자는 중요한 원문·판단·질문·실행 결과를 확인하고 변경을 관련 세션에 전달한다. T1의 모든 정리나 T2의 전체 뼈대가 완성될 때까지 나머지 세션이 기다리는 구조로 운영하지 않는다.
